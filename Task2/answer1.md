# Распознавать и оцифровывать сканы документов, приложенных к кредитной заявке

## Готовность данных

| Поле | Значение |
| --- | --- | 
| Источник правильного ответа | Сам пользователь - он проверяет, что данные распознались корректно | 
| Качество | Качество должно быть высокое - у нас есть накопленная база документов, которые распознавались вручную |
| Объём по важному классу | Нет какого-то важного класса |
| Разметка | Есть набор распознанных вручную документов |
| Cмещение отбора | - | 
| Репрезентативность | не известно |
| Право использовать | Нужно уточнить у юристов - могут быть чувствительные данные |
| Владелец | Отдел кредитования |
| Вердикт | Пока использовать нельзя - нужно уточнить у юристов |

## Размещение

Здесь лучше выбрать on-premise, так как в сканах документов могут быть чувствительные данные. То есть они не должны покидать наш контур.
Для проверки гипотезы можно пробовать выделенный контур провайдера и распознавать документы, в которых нет персональных данных. Публичный API лучше не использовать, чтобы другие пользователи этого API случайно не получили наши данные.
## Выбор модели

| Вариант | За | Против |
| --- | --- | --- |
| Готовая OCR-библиотека с открытым кодом + правила извлечения полей | Бесплатно, работает в своём контуре, легко поднять | Плохо читает фотографии, печати, рукописный текст. Правила придётся писать под каждый тип справки |
| Коммерческая OCR с лицензией на своё железо | Хорошее качество на сканах и таблицах, есть готовые шаблоны российских документов | Платно, зависимость от вендора |
| Мультимодальная LLM через публичное API | Одна модель и распознаёт, и сразу извлекает поля, ничего не обучаем | Документы с персональными данными уходят наружу — прямо противоречит вердикту по данным. Ответ не гарантирован по схеме, поля можно выдумать |
| Готовая OCR (распознавание) + своя дообученная модель извлечения полей (NER) | OCR не обучаем, обучаем только извлечение полей, где и есть наша специфика. Всё внутри контура | Нужен размеченный набор под извлечение, нужна своя команда сопровождения |

**Выбрали: готовая OCR + своя модель извлечения полей.** OCR с нуля учить незачем, это решённая задача. Специфика у нас не в чтении букв, а в том, какие именно поля нужны из справки о доходах и из отчётности, — вот эту часть и обучаем на своих данных. Обучающий набор берём из исправлений клиента и оператора: человек и так подтверждает поля, поэтому метки копятся сами.

Отдельная модель для классификации типа документа не нужна на старте: тип можно спрашивать у клиента при загрузке, а формат файла проверять кодом.

## Проверка

Проверяем на золотом наборе из 300–500 документов, размеченных вручную: паспорта, справки о доходах, бухгалтерская отчётность, в том числе намеренно плохие — фотографии с телефона, перекошенные, серые, со штампами поверх текста.

Что считаем:

* Точность по каждому обязательному полю отдельно, а не «в среднем по документу». Ошибка в сумме дохода дороже ошибки в отчестве.
* Доля документов, которые прошли без единой правки человеком. Это главная метрика: именно она превращается в экономию времени.
* Доля правок, которые внёс клиент.
* Доля полей, для которых модель не нашла подтверждения на скане.

Порог годности: не меньше 70 % документов проходят без правок, и ни по одному обязательному полю точность не ниже 95 %. Ниже этого андеррайтинг будет перепроверять всё подряд и полутора часов на пакет мы не сэкономим.

Гипотезу проверяем на документах без персональных данных — на них можно посмотреть и облачные варианты, не нарушая ограничений.

# ADR-002. Модель для распознавания сканов документов

Статус: предварительное
Дата: 05.09.2026
Инициатива: Распознавать и оцифровывать сканы документов, приложенных к кредитной заявке

## Контекст
Андеррайтинг разбирает пакет документов по заявке в среднем полтора часа. Часть этого времени — ручной перенос данных из сканов в форму. Документы содержат персональные данные, поэтому вердикт по данным — «пока использовать нельзя, нужно уточнить у юристов».

## Жёсткие ограничения
Сканы не должны покидать контур банка. Клиент обязательно подтверждает распознанные данные перед подачей заявки.

## Сравнительные критерии
Безопасность данных (5), качество на плохих сканах (4), стоимость внедрения (2), скорость получения результата (1 — задержка в минуты допустима).

## Рассмотренные варианты
| Вариант | Почему отклонён или выбран |
| --- | --- |
| Только open-source OCR + правила | Отклонён: качество на фотографиях и печатях низкое, правила под каждый тип документа не масштабируются |
| Мультимодальная LLM через публичное API | Отклонён: персональные данные уходят наружу, ответ не гарантирован по схеме |
| Коммерческая OCR на своём железе | Оставили как запасной вариант, если качество открытой OCR не дотянет до порога |
| Готовая OCR + своя модель извлечения полей | Выбран: OCR не изобретаем, обучаем только то, где наша специфика, всё остаётся в контуре |

## Решение
Готовая предобученная OCR внутри контура плюс своя модель извлечения полей, дообучаемая на исправлениях клиента и оператора. Гипотезу проверяем на документах без персональных данных.

## Допущения
| Допущение | Источник | Критично |
| --- | --- | --- |
| Юристы разрешат обрабатывать сканы с персональными данными | Юристы | Да, без этого проект не стартует |
| Открытая OCR даёт приемлемое качество на наших сканах | Проверка на золотом наборе | Да, иначе покупаем коммерческую лицензию |
| Клиент готов проверять и править поля в форме | Отдел кредитования | Средне: без подтверждения не будет меток для дообучения |

## Риски и что с ними делаем
Модель уверенно распознала неверное значение — поэтому каждое поле показываем рядом с фрагментом скана и требуем подтверждения. Поддельная справка — это отдельная инициатива, здесь мы её не ловим и на распознавание не полагаемся.

## Триггеры пересмотра
Меняется законодательство по персональным данным, появляются новые типы документов, доля ручных правок растёт две недели подряд.
