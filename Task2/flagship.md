# Автоматическое выявление подозрительных операций по счетам

## Готовность данных

| Поле | Значение |
| --- | --- | 
| Источник правильного ответа | В постановке задачи говорится, что размеченных данных нет. Поэтому либо накапливать базу, либо разметить руками имеющийся набор данных | 
| Качество | Могут встречаться неправильно определенные операции. Для этого можно размечать данные несколькими экспертами и выбирать ответ, который проставило большинство |

## Размещение 

Лучше выбрать on-premise, так как нам важна скорость, независимость от других сервисов (тем более внешних) и безопасность данных.

## Проверка

* Нужно по ровну примеров с отрицательным и положительным вердиктом, тк у модели точность может быть 0.99, но при этом кейсов в фродом - меньше 0.01. Тогда будет показывать высокую точность даже при неправильном определении реального фрода почти всегда. 
* Нужно, чтобы она точно определяла хотя бы 20000/35000 = ~57% операций. Остальные, если сомневается, отправляла на ручной разбор.

# ADR-001. Выбор решения для автоматического выявления подозрительных операций по счетам
Статус: предварительное
Дата: 02.09.2026
Инициатива: Автоматическое выявление подозрительных операций по счетам

## Контекст
Банку необходимо обнаруживать подозрительные операции (отмывание денег, схемные операции, дробление и тд) для соблюдения требований регуляторов.
Пороговые правила и внешние сигналы помечают около 35 тыс. операций в месяц. Служба финансового мониторинга успевает разобрать примерно 10 тыс. 
Пропущенные операции - штрафы от регулятора. Ложно замороженные операции - недовольные клиенты.

## Жёсткие ограничения
Работаем с персональными данными клиентов. Они не должны утечь.
Проверка на фрод - не инициатива банка, а обязанность по закону. Такая проверка должна осуществляться перед любой операцией.

## Сравнительные критерии
Безопасность данных (5), скорость ответа (3), стоимость проведение эксперимента для проверки жизнеспособности (1), стоимость реализации целевого решения (2)

## Рассмотренные варианты
| Вариант | За | Против | Почему отклонён или выбран |
|---|---|---|---|
| Публичный API | Можно дёшево и быстро проверить эксперимент и реализовать целевое решение | Небезопасная обработка данных, ресурсы делятся с другими клиентами - сильная зависимость по скорости ответа | Важнее безопасность данных и скорость ответа |
| Выделенный контур провайдера | Можно дёшево и быстро проверить и запустить, не такая сильная зависимость по ресурсам | Данные отправляются за пределы контура, зависимость по ресурсам все-таки остается | Зависимость от провайдера и низкая безопасность данных отвергают это решение |
| Self-hosting в облаке | Целевое решение дешевле в реализации, чем on-premise. При необходимости легко масштабируется. Зависимость по ресурсам не ощущается | Данные гоняются по сети | Можно рассмотреть, если уточним у юристов, какие данные безопасно гонять по внешней сети и что их достаточно для работы модели |
| On-premise | Данные остаются внутри контура, нет зависимости по ресурсам (можно настроить стабильно быстрый ответ) | Дорогое решение - нужно железо, постоянная поддержка работоспособности, масштабирование сложнее | Выбрали это решение, так как безопасность данных важнее всего |

## Решение
Для пилота можно попробовать Self-hosting в облаке. Для целевого решения - On-premise.
## Допущения
| Допущение | Источник | Критично для вывода |
|---|---|---|
| Некоторые данные пользователя безопасно гонять по сети | Юристы | Да |
| Облачный провайдер выделить нам достаточное количество ресурсов | Документация и поддержка провайдера | Да |

## Риски и что с ними делаем
## План выхода
Если условия остаются выгоднее, чем делать on-premise решение - остаемся в облаке. Если выгоднее самим - перевозим на свое железо. Можно заранее зарезервировать железо под потенциальный переезд, чтобы чуть ускорить в будущем процесс переезда.
## Триггеры пересмотра
Провайдер меняет условия, меняется законодательство, растет число операций в день
