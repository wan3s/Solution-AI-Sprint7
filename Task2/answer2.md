# Маршрутизировать входящие обращения по нужным отделам

## Готовность данных

| Поле | Значение |
| --- | --- | 
| Источник правильного ответа | По истории обращений можно понять, в какой отдель роутили вопрос | 
| Качество | Могут быть неточности, если оператор сам ошибался |
| Объём по важному классу | Здесь все классы равны |
| Разметка | Автоматическая|
| Cмещение отбора | - | 
| Репрезентативность | Высокая |
| Право использовать | Каких-то юридических подвохов тут не должно быть |
| Владелец | Поддержка |
| Вердикт | Готово |

## Размещение

Можно использовать публичное API, если оно готово выдерживать нашу нагрузку. Можно разместить в выделенном провайдере облака. Тогда можно будет легко масштабировать решение при росте нагрузки.
## Выбор модели

| Вариант | За | Против |
| --- | --- | --- |
| Правила по ключевым словам | Прозрачно, работает сразу, ничего не обучаем | Клиенты пишут своими словами, а не терминами банка. Список правил быстро становится неподъёмным |
| Классификатор на эмбеддингах текста (логистическая регрессия или CatBoost поверх готовой модели эмбеддингов) | Дёшево, быстро, обучается на нашей истории обращений, легко переобучать | Не понимает длинные и путаные обращения, где несколько тем сразу |
| Дообученный небольшой энкодер (ruBERT и подобные) | Заметно лучше на живом тексте, всё ещё дёшев в вызове | Нужно железо для дообучения и человек, который это сопровождает |
| LLM через публичное API с промптом, без обучения | Работает без разметки, сразу понимает новые отделы | Дороже за вызов, зависимость от провайдера, ответ нужно проверять по справочнику отделов |

**Выбрали: дообученный небольшой энкодер-классификатор.** Данные готовы — история обращений с автоматической разметкой (куда в итоге ушло обращение), классы сбалансированы, задача типовая для NLP. Такая модель дешева в вызове и полностью наша.

Правила по ключевым словам оставляем не как альтернативу, а как первый шаг и как запасной путь: явные случаи (VIP-клиент, жалоба на блокировку) должны уходить в нужный отдел мимо модели, а при недоступности модели маршрутизируем по ключевым словам и дальше на общую линию.

LLM через API держим в уме для холодного старта: когда появляется новый отдел, меток по нему ещё нет, и модель без обучения может закрывать этот класс, пока не накопится история.

## Проверка

Обучаем на истории обращений, но разбиваем выборку **по времени, а не случайно**: обучаемся на прошлых месяцах, проверяемся на последних. Случайное разбиение здесь врёт, потому что отделы появлялись в разное время и модель «подсмотрит» будущее.

Что считаем:

* Доля правильно направленных обращений в целом и отдельно по каждому отделу — маленькие отделы не должны утонуть в среднем показателе.
* Сравнение с базовой линией: сколько обращений операторы переадресуют сейчас. Модель должна ошибаться реже человека на общей линии, иначе смысла нет.
* Доля обращений, которые уходят на общую линию из-за низкой уверенности. Если их больше трети, мы просто переложили работу обратно на людей.
* Отдельно смотрим на обращения по недавно появившимся отделам — там меток мало и модель будет ошибаться чаще.

Порог годности: не меньше 85 % правильных маршрутов при доле обращений на общей линии не выше 15 %.

Дальше — теневой режим: модель предлагает отдел, но обращение маршрутизирует человек, а мы сравниваем предложение с его решением. Это дешёвый способ проверить модель, ничем не рискуя: цена ошибки здесь низкая, оператор отдела всегда может переадресовать.

# ADR-003. Модель для маршрутизации обращений

Статус: предварительное
Дата: 05.09.2026
Инициатива: Маршрутизировать входящие обращения по нужным отделам

## Контекст
Обращения распределяет по отделам оператор общей линии. Данные готовы: есть история, куда в итоге попало обращение, разметка получается автоматически. Цена ошибки низкая — оператор отдела переадресует обращение дальше.

## Жёсткие ограничения
Обращение пишет клиент, в тексте могут оказаться номера карт и счетов. Наружу такой текст уходить не должен без обезличивания. Ответ клиенту допускает задержку в несколько минут.

## Сравнительные критерии
Стоимость вызова и владения (4), качество на живом тексте (4), скорость внедрения (3), независимость от внешнего провайдера (2). Безопасность данных здесь весит меньше, чем во флагмане: обращение — не платёжная операция, а чувствительные фрагменты можно замаскировать.

## Рассмотренные варианты
| Вариант | Почему отклонён или выбран |
| --- | --- |
| Только правила по ключевым словам | Отклонён как основное решение, оставлен как запасной путь и как обработчик явных случаев |
| Классификатор на эмбеддингах | Отклонён: проще, но заметно слабее на длинных и путаных обращениях |
| LLM через публичное API | Отклонён как основное решение: дороже и зависимость от провайдера. Оставлен для холодного старта новых отделов |
| Дообученный небольшой энкодер | Выбран: данные готовы, вызов дешёвый, качество достаточное, модель наша |

## Решение
Дообученный небольшой энкодер-классификатор, размещённый в выделенном контуре облачного провайдера, чтобы легко масштабироваться при росте нагрузки. Перед отправкой текста наружу маскируем номера карт, счетов и паспортов. Ответ модели — код отдела, который сверяем со справочником отделов.

## Допущения
| Допущение | Источник | Критично |
| --- | --- | --- |
| История обращений отражает правильный отдел | Поддержка | Да: если операторы часто ошибались, модель научится ошибаться так же |
| Отделы и их зоны ответственности не меняются каждый месяц | Поддержка | Средне: при частых изменениях придётся переобучать чаще |
| Маскирования достаточно, чтобы отправлять текст провайдеру | Юристы, безопасность | Да: иначе переносим модель в свой контур |

## Риски и что с ними делаем
Обращение по новому отделу, которого не было в обучении, — уходит на общую линию, а не в случайный отдел. Провайдер недоступен — маршрутизируем по ключевым словам. Модель систематически ошибается по одному отделу — видим по доле переадресаций в разрезе отделов и переобучаем.

## Триггеры пересмотра
Появляется новый отдел, растёт доля переадресаций, провайдер меняет условия или перестаёт держать нагрузку.
